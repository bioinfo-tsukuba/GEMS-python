## 目的

これまで実装しきれていなかった、Experimentのライフサイクルに関する2つの機能を実装する。

1. **試料分割と履歴継承**：細胞の取り分けなど、1つの試料から複数の試料を作る操作を表現する。親の履歴・出自を引き継ぎ、それぞれの子を独立したExperimentとして進める。
2. **終了したExperimentの自己消去**：Experimentが終了を明示したとき、管理対象から自動的に削除する。従来必要だった手動削除を不要にする。

初期対象はmulti-machineの仮想実験。試料分割は、明示的に有効化する試験機能として導入する。基本動作、再試行、保存・再開を小規模で検証した後、分割後のスケジューリング規模を評価する。

登録を保持したまま開始を保留する仕組みと、計画結果に応じた再試行・STOPの方針は、分割で生まれた子だけでなく通常のExperiment登録にも既定で適用する。

## 背景と現状

### 1. 論文で制約として挙げた試料分割

論文 *GEMS: a deterministic finite automaton framework for adaptive laboratory automation*（Digital Discovery, 2026, 5, 1411–1424、DOI `10.1039/D5DD00409H`、Discussion p.1423）では、単一試料を複数の子試料へ分割するネイティブ機能がないことを制約として挙げている。

履歴を引き継いだ複数のExperimentを個別に登録する回避策では、分割という1つの操作、親子関係、親の終了、子の登録を整合して管理できない。細胞の取り分け後に、共通の出自を持つ子をそれぞれ独立に培養・観測する表現が必要である。

### 2. 終了した実験の削除が手動

Experimentの状態遷移と、管理対象からの削除が連動していない。実験が終了しても、削除APIを別途呼び出す必要がある。実験自身が終了を明示し、管理層がそのExperimentを削除する機能を実装する。

これは終了管理の未実装部分を補う課題であり、試料分割とは別に完了条件を設ける。

### 確認した実装

確認対象はmain `2140ab1919adb453122fd964cfdb3a7c216c74b9`。

- 通常の状態遷移は`transition_function -> str`で次のStateを1つ選び、同じUUIDのExperimentで次のTask群を生成する。
- 次のTask群が空なら計画対象に追加しないが、そのExperiment自体は管理一覧に残る。
- `delete_experiment_with_experiment_uuid`は明示的な呼出しを必要とし、通常の状態遷移から自動的には呼ばれない。
- `add_experiment`は1件の登録ごとに再計画する。保存も既定では登録ごとに行う。専用の分割イベント・親子管理APIはない。
- 通常登録にも適用する保留状態や、計画失敗の原因に応じた倍増再試行・STOPの共通処理は未実装である。
- JSONとpickleは順次書込みであり、書込み中断時に両形式を同じ保存世代として確定する仕組みはない。

## 目指す振舞い

| 場合 | 管理対象のExperiment | 履歴・記録 |
| --- | --- | --- |
| 従来の通常進行 | 同じExperimentが状態遷移する。終了後の削除は別途手動で行う | 同じExperimentに観測履歴を追加する |
| 自己消去 | 終了を明示したExperimentを自動削除する。子は作らない | UUID・履歴・終了理由などを別の終了記録として残す |
| 試料分割 | 分割成功時に親Experimentを削除し、複数の子Experimentを一括登録する | 親の出自履歴を保持し、子が履歴を引き継ぐ。分割後の観測は子ごとに独立して管理する |

ここで「削除」は、Experimentを実行管理の対象から取り除くことを指す。履歴や出自記録の消去、物理試料の廃棄を意味しない。分割後の残余を継続する場合も、残余を子として表現する。

子1と子2は、それぞれ独立したExperimentである。UUID、履歴、State、新規Taskを別々に持つ。装置は共有するため、スケジュールは他の活動中Experimentも含めてまとめて計算する。

## 機能要件

### A. 終了したExperimentの自己消去

- 実験手順側が終了を明示でき、管理層が終了を確認してExperimentを自動削除する。
- 単にState名が`FinishState`や`ExpireState`であること、次のTask群が空であることだけを根拠に、既存のExperimentを一律に削除しない。終了の宣言方法は実装前に契約として定義する。
- 終了したExperimentの新しいTaskを生成せず、対応するTask群を計画対象から外す。未完了の必要な処理があるExperimentを通常終了として誤削除しない。
- UUID、終了時刻・理由、履歴、設定・機能版を、活動中Experimentとは別の終了記録として保存する。
- 同じ終了要求・完了応答を再送しても、削除と終了記録が重複せず、保存再開後に終了したExperimentが復活しない。
- 他のExperimentの履歴・State・実行進捗を変更しない。残りの実験を継続でき、全Experiment終了時にも正常に停止できる。

### B. 試料分割と子の独立性

- 分割は既定で無効とし、明示的に有効化した場合のみ扱う。既存の`transition_function -> str`を一律に別の戻り値型へ変更する方式は初期対象にしない。
- 管理層が分割要求、分割操作の完了確認、確定を扱う。分割を予定した段階では子を活動させない。
- 安定した要求ID、親UUID、子UUID群、論理時刻、親の出自スナップショット、初期条件とその由来、設定・機能版を記録する。系譜はUUID参照で持ち、親子オブジェクトの循環参照を作らない。
- 各子を独立したExperimentとして生成する。親のTask、機械割当、実行進捗、Stateの動的進捗を複製しない。
- 分割時点までの親履歴を子の出自として引き継ぎ、状態判断に必要な分割前の履歴を利用できるようにする。親由来の観測と、子の初期観測・分割後の観測を区別する。
- 子1への観測追加・状態更新で、子2の履歴や親の出自記録が変化しない。科学的な値のコピー、選択、換算はプロトコルに明示する。
- 全子の仕様、UUID、初期状態・観測と、必要な種類の機械の登録状況を事前検証する。仕様不正や分割完了確認失敗では分割を確定せず、部分登録を起こさない。機械の未登録は仕様不正と区別し、全子を登録したうえで、該当する子だけを装置待ちにする。
- 分割成功後、分割イベントの記録、親Experimentの削除、全子登録を1つの変更として確定する。一部の子だけを登録しない。
- 確定後は、必要な種類の機械が未登録の未開始Task群を除き、計画対象の子と他の活動中Experimentをまとめて再計画する。1回の計画試行につき一括で計算し、`UNKNOWN`の場合の再試行はCの方針に従う。既存の個別追加・個別削除APIを順番に呼んで、その都度再計画・保存する実装にはしない。

### C. 失敗、再試行、保存・再開

#### 通常登録と子の登録に共通する保留

- **保留は、Experimentの登録を保持し、新しいTaskの開始を止める状態**とする。削除や登録取消しを意味しない。通常のExperiment登録にも既定で適用し、理由を警告として出す。
- 登録時は最初のTaskだけでなく、最初に生成されるTask群全体について入力検査を行い、他のExperimentの予約も含めて計画する。後続のTask群は、その生成時に同じ検査・計画を行う。未生成の将来のTaskまで登録時に確定する前提にはしない。
- 必要な種類の機械が未登録なら、そのExperimentだけを装置待ちとして保留する。その未開始Task群を計画対象から除き、他のExperimentのスケジューリングと実験実行は続ける。分割の場合も全子の登録と親の削除を維持し、装置待ちの子だけを保留する。
- 登録済みの機械が使用中であることだけでは装置待ちにしない。予約と整合する将来の開始時刻を持つ有効な計画が得られれば、通常の実行待ちとして扱う。
- 保留中に有効な計画が得られたら、同じUUIDのExperimentで開始できるようにする。すでに実行中のTaskの時刻・機械割当と予約は維持し、未開始Task群の除外によって実行中の予約を消さない。

#### 入力検査・計画結果ごとの動作

| 検出内容 | 判定 | 動作 |
| --- | --- | --- |
| 有効な計画が得られた | `OPTIMAL` / `FEASIBLE` | 計画を採用する。最適性が未証明でも`FEASIBLE`なら実行できる |
| 有効な計画を見つける前に探索が終了した | `UNKNOWN` | 警告を出し、既定では探索時間の上限を倍にして再試行する。設定で再試行せずSTOPする動作も選べる |
| 固定済みの予約が同一機械で重複するなど、制約が矛盾する | `INFEASIBLE`、または事前検査で制約矛盾を検出 | 全体STOP。Errorとして理由を表示する |
| 必要な種類の機械が未登録 | 入力検査で検出 | 警告を出し、該当Experimentだけを装置待ちにする。他のExperimentの計画・実行は継続する |
| 負の処理時間など、仕様自体が不正 | 入力検査で検出 | 全体STOP。Errorとして理由を表示する |

- `UNKNOWN`は実行不能の証明として扱わない。有効な計画が得られるまで新しい計画を適用せず、その計画を必要とするTaskの開始を保留する。
- 倍増するのはCP-SATに設定する各試行の探索時間上限であり、実際に消費した時間ではない。初回を`T`として、`T → 2T → 4T …`と再試行する。
- 無制限の再試行にはしない。探索時間または再試行回数に必ず上限を設ける。設定した上限を超える再試行は行わず、上限内で有効な計画が得られなければ全体STOPし、Errorで探索終了と上限到達を明示する。
- `UNKNOWN`時にSTOPする設定でも、探索結果の警告を出す。再試行する設定では各回の結果・探索時間上限・再試行回数を記録する。初回探索時間、再試行の方針、上限設定を保存する。具体的な上限値は実装前に確定する。
- 再試行ではExperimentの登録や分割確定をやり直さず、同じ登録済みExperimentを対象に探索する。入力が変わった場合は検査・再計画を行い、古い入力に対する計画を適用しない。

#### STOPと診断

- **全体STOPは、管理ループを停止し、全Experimentで新しいTaskを開始しない状態**とする。装置待ちによる該当Experimentだけの保留と区別する。
- 実行中の装置操作を強制中断する意味は持たせない。実行中Taskの完了確認・記録をどう扱うかは実装前に定義する。
- Errorには、判定、理由、関係するExperiment UUID・Task・機械ID・予約区間など、原因を追跡するための情報を表示する。負の処理時間や固定予約の重複などは事前検査で具体的に示す。
- solverが`INFEASIBLE`を返した場合も、特定できた矛盾を示す。矛盾する制約を特定できない場合はその旨を明示し、入力・設定・判定を再現可能な形で保存する。推測した原因を確定した理由として表示しない。
- 分割確定後に保留・再試行・STOPとなっても、親子の出自、分割イベント、登録済みの全子を保持する。親を活動中に戻したり、一部の子だけを削除したりしない。

#### 再送と保存・再開

- 同じ分割要求IDと同じ仕様は、同じ子UUID群とイベントを返す。重複応答で子を増やさない。同じIDで異なる仕様は衝突として扱う。
- 自己消去と分割の要求・確定・再送を識別し、削除済みのUUIDも終了記録や系譜から追跡できるようにする。
- JSON/pickleに活動中・保留のExperiment、保留理由、管理ループのSTOP状態、再試行の設定・進捗、終了記録、親子関係、イベント、初期条件・由来を保存し、別プロセスで再開できるようにする。再開で登録が重複したり、再試行の上限が失われたりしない。
- 記録と活動／保留集合を同じ保存世代として確定する。書込み中断時の不整合を検出・復旧し、復旧不能な状態は報告する。
- 対応するPandas/Polarsバックエンドでも、履歴・初期条件・系譜・状態が一致する。保存形式・機能版と旧形式の読込み方針を文書化する。

## 実装・検証の順序

1. 既定`o`の通常更新を小規模で確認し、終了の明示方法、管理対象と終了記録の区別、履歴継承の契約を定義する。
2. 1つのExperimentの自己消去を実装する。終了前の維持、終了時の削除、終了記録、他の実験の継続、全終了時の停止を確認する。
3. 仮想実験で1親→2子を1回分割する。親の削除、親子UUID、履歴継承、独立した子の通常進行、一括登録を確認する。
4. 通常登録と子の登録の両方で、装置待ちと他の実験の継続、`FEASIBLE`の採用、`UNKNOWN`の倍増再試行・STOP設定・上限到達、制約矛盾・不正仕様の全体STOPと理由表示を確認する。同じ小規模条件で、終了・分割の再送、分割完了確認失敗、保留からの再開、保存・別プロセス再開、書込み中断も確認する。
5. 2親→4子などの小規模負荷で、分割処理、履歴管理、再計画、保存の時間とメモリを測る。
6. 親数・子数・分割頻度を1つずつ増やし、分割後の規模を評価する。

## 通常更新との依存関係・規模評価

#23の通常更新の検証、計測器、独立した出力検査、小規模基準を再利用する。自己消去・分割を導入する前提は、既定`o`の正常な更新経路が確認できることであり、大規模性能目標の達成や旧`s`・`f`の全作業完了を追加の必須条件にしない。

分割後の規模評価では、従来の本Issueの計画どおり、計画全体が1秒／60秒以内となる負荷・規模を測る。**#23の1秒／60秒はCP-SATの探索上限であり、計画全体時間の保証ではない。** 計測器を再利用しても両者を同じ条件として扱わない。本Issueの計画全体時間の開始・終了点、探索上限、反復数、実行費用上限は、規模評価の実行前に確定する。

- 分割条件、観測、処理時間、実験追加規則を非確率的に固定する。
- 活動数、群数・タスク数・機械数、計画・更新・分割・保存の時間、遅延、系譜・履歴のメモリを記録する。
- `UNKNOWN`の再試行では各試行の探索上限と実測時間、累積時間を記録する。探索上限を増やして得た計画を、初回の時間条件で成功した結果として数えない。
- 同じ活動タスク・機械条件の分割なし負荷と比較し、タスク数増加と分割・履歴・保存の追加負荷を区別する。
- 有効な計画、計画全体の時間超過、解なし、証明済み実行不能、不正出力を区別する。時間切れを実行不能の証明と扱わない。
- 入力ハッシュ、対象commit、設定、依存版、環境、再現コマンド、結果CSV/JSON・要約、失敗入力を保存する。

## 完了条件

### 自己消去

- [ ] 終了を明示したExperimentが手動操作なしで管理対象から削除され、子や新しいTaskを生成しない。
- [ ] 終了前のExperimentを誤削除せず、他のExperimentの履歴・State・進捗と、実行中Taskの時刻・割当を維持する。
- [ ] UUID・履歴・終了時刻・理由を別の記録として保存し、全終了時にも正常に停止する。
- [ ] 再送で削除・終了記録が重複せず、保存・別プロセス再開後に終了したExperimentが復活しない。

### 分割・履歴継承

- [ ] 分割有効時のみ1親→複数子を表現でき、無効時の通常実験が従来どおり動く。
- [ ] 分割成功時の親削除、全子登録、分割イベント、親子UUID、初期条件の由来が整合する。
- [ ] 各子が独立したExperimentとして、親の履歴を利用しつつ自分の観測・State・Taskを進められる。
- [ ] 子1の更新が子2や親の出自を変更せず、親のTask・機械割当・実行進捗・Stateの動的進捗を引き継がない。
- [ ] 不正な子仕様・完了確認失敗で部分登録を起こさない。機械未登録では全子を登録して該当する子だけを保留し、確定後の保留・STOPでも親子の出自と全子登録を維持する。

### 通常登録・保留・計画結果・STOP

- [ ] 通常登録にも保留を既定で適用し、最初のTask群全体を検査する。保留理由を警告で表示し、登録とUUIDを維持する。
- [ ] 必要な種類の機械が未登録のExperimentだけを保留し、他のExperimentの計画・実行を継続できる。装置が使用中でも有効な将来の計画が得られる場合は装置待ちにしない。
- [ ] 必要な機械の登録後に再計画でき、保留中のExperimentが同じUUIDで開始できる。実行中Taskの時刻・割当・予約を維持する。
- [ ] `OPTIMAL`と`FEASIBLE`の計画を採用し、`UNKNOWN`を実行不能の証明と扱わない。
- [ ] `UNKNOWN`で警告を出し、既定では探索時間上限を倍増して再試行する。再試行なしのSTOP設定と、上限到達時の全体STOP・Errorも検証する。
- [ ] 固定予約の重複などの制約矛盾と、負の処理時間などの不正仕様で全体STOPする。Errorに理由と対象情報を示し、特定できない矛盾はその旨と再現入力を残す。
- [ ] 全体STOPで管理ループと新しいTaskの開始が停止し、実行中の装置操作を暗黙に強制中断しない。

### 再試行・保存再開

- [ ] 確定前後と再開後の再送で、子とイベントが増えない。要求IDと仕様の衝突を検出する。
- [ ] 対応するDataFrameバックエンドとJSON/pickleで、履歴、初期条件、系譜、活動／保留状態・理由、STOP状態、再試行の設定・進捗、終了記録が一致する。
- [ ] 要求前、完了確認後、確定後、装置待ち、`UNKNOWN`の再試行中、STOP時の保存・別プロセス再開を確認し、再試行上限や登録が維持される。
- [ ] 書込み中断の障害注入で保存世代の整合性を検証し、復旧不能な状態を検出・報告する。
- [ ] 保存形式・機能版、旧形式の扱い、再現手順、確認結果と未検証範囲を文書化する。

### 分割後の規模評価

- [ ] 計画全体時間と探索上限を分け、評価設定・実行費用上限を確定して記録する。
- [ ] 決定的な負荷で1秒／60秒の計画全体時間を測り、同じ活動タスク・機械条件の分割なし負荷と比較する。
- [ ] 規模、時間、遅延、メモリ、有効性、反復結果、失敗境界とばらつきを保存し、測定環境・負荷での結論を報告する。

## 実装前に確定する事項・対象外

- 終了を明示するAPI・終了宣言方法と、既存プロトコルへの適用方法。
- 親の継承履歴と子自身の観測をStateへ渡す方法。出自参照、由来付きの独立コピーなどの保存・入力契約を定義し、履歴の混同や二重計上を避ける。
- 子の初期State・観測の生成／変換規則、分割量・単位・残余・容器IDの初期対応範囲。
- 初回探索時間、倍増再試行の探索時間上限・回数上限の具体値と設定API。倍増再試行を既定とし、再試行なしでSTOPする選択肢を設ける方針は確定済み。
- 機械登録後に装置待ちから再計画する契機（自動／明示操作）と、STOPからの再開操作・条件。保存読込みを開始許可とするかも明示し、暗黙に決めない。
- STOP後の実行中Taskの完了確認・記録方法。全体STOPは新しいTaskの開始を止める方針であり、装置操作の強制中断を要求しない。
- 分割後の親Experimentは削除する。親を活動中のまま継続する方式は初期対象に含めず、残余の継続は子として表現する。
- 合流・共同判断、実行中処理の強制中断、実機による自動分割、装置応答喪失時の物理的復旧、確率的な実験摂動は対象外。
- 論理的な二重登録防止は、実機の不可逆操作を1回だけ実行する保証とは異なる。
- 選定した仮想プロトコルの試験機能と実測評価を対象とし、任意の実験手順・施設規模での適用や、予算内の最適解を保証しない。
